Primer 1 · The agentic loop and its stop reasons

Every agent built on the Claude API — including Claude Code and the Agent SDK — is the same loop. You must be able to recite it, because a third of the exam's architecture questions are really questions about where in this loop a failure occurred.

1. Send a request:  messages + tools + system  →  POST /v1/messages
2. Read response.stop_reason
     "tool_use"  → execute the tool(s), append tool_result, GOTO 1
     "end_turn"  → Claude is done; the turn is complete
     other       → handle per the table below
3. Repeat until a terminal stop_reason, a turn budget, or a wall-clock budget is hit.
Rule — the loop is driven by stop_reason, never by text Detecting completion by string-matching the assistant's prose ("looks like it said 'all done'") is a guaranteed-wrong answer. stop_reason is the only contractual completion signal.

Stop reasons you must know

ValueMeaningCorrect handling
tool_useResponse contains one or more tool_use blocks and Claude is waiting on resultsExecute each tool, return a tool_result for every tool_use_id, continue the loop
end_turnClaude finished naturallyTerminal. Hand the result to your resolution/verification step
max_tokensOutput hit max_tokens mid-generation — the response is truncatedNot a success. Continue generation or re-run with a larger budget; never parse truncated output as final
stop_sequenceA custom stop sequence was emittedTerminal for your grammar; treat per your protocol
pause_turnA long-running server tool turn was pausedContinue the turn by sending the response back unchanged
refusalClaude declined for safety reasonsTerminal. Route to human — do not retry the identical prompt in a loop
model_context_window_exceededInput exceeded the windowCompact/summarize and retry; do not silently drop the request

Tool result formatting rules that get tested

  • Every tool_use block must be answered by a tool_result with the matching tool_use_id, in the immediately following user message.
  • Inside that user message, tool_result blocks come first; any text comes after. Text before a tool result is a 400 error.
  • Tool failures are reported as a normal tool_result with "is_error": true and an instructive message — not by throwing away the turn.
  • Tool results carry untrusted external content. Keep third-party text inside tool_result blocks, never promoted into the system prompt.
{
  "role": "user",
  "content": [
    { "type": "tool_result",
      "tool_use_id": "toolu_01A...",
      "content": "Rate limit exceeded on orders-api. Retry after 60s.",
      "is_error": true }
  ]
}
Trap "content": "failed" is the classic wrong answer. An error string that does not say what failed, whether it is retryable, and what to try next forces the model to guess, and guessing produces retry storms or fabricated results.

Coordinator / subagent topology

Multi-agent questions almost always reduce to three facts:

  1. Subagents start with a clean context. They do not inherit the coordinator's conversation history. Anything they need must be passed explicitly in the delegation prompt. (The exception is a fork, which does inherit the full parent conversation.)
  2. Topology is hub-and-spoke. One coordinator decomposes, dispatches, merges, and owns the final answer. Peer-to-peer chatter between subagents is the wrong answer.
  3. Coverage failures are decomposition failures. If subagents each did their job well but the merged report has a gap, the bug is in how the coordinator scoped the subtasks — not in the subagents, and not fixable by adding more of them.

Topic 1 · Orchestration-layer safeguards for session termination

Objective: Design orchestration-layer safeguards ensuring every agent session ends with a completed resolution or human escalation, regardless of how the agentic loop terminates. Agentic Architecture · 27%

The problem, stated precisely

An agentic loop can stop for at least eight reasons, and only one of them is "the work is done". Left alone, the other seven produce a silent drop: the customer's ticket, the incident, the transaction ends in no state at all. The exam calls this the terminal-state guarantee, and the correct architecture puts it in the orchestration layer — code that wraps the loop — not in the prompt.

The invariant to design toward Every session terminates in exactly one recorded state: RESOLVED (with a verified outcome) or ESCALATED (with a human owner and a handoff payload). There is no third state. "Loop ended" is not a state; it is an event that must be mapped onto one of the two.

Enumerate every exit path

Termination pathWhat naïve code doesWhat the safeguard must do
stop_reason: end_turn with a resolutionReturn the textVerify the resolution actually happened (tool receipt / DB state), then close as RESOLVED
stop_reason: end_turn with no action takenReturn the text — looks like successDetect the missing terminal action and escalate; a polite non-answer is not a resolution
stop_reason: max_tokensParse the truncated outputTreat as incomplete: continue or escalate. Never accept truncated output as final
stop_reason: refusalRetry the same promptTerminal — escalate to a human immediately
Turn budget exhausted (max iterations)Return whatever is in the bufferEscalate with the partial-progress transcript attached
Wall-clock / SLA timeoutNothing — the request just diesA watchdog outside the loop fires and escalates
Unhandled exception in tool execution500 to the callerCatch at the orchestrator boundary, persist state, escalate
Process crash / deploy restartSession vanishesDurable session state + a reaper job that sweeps sessions stuck in a non-terminal state
User abandons mid-sessionSession idles foreverIdle timeout → resolve-or-escalate sweep
Trap — "add a retry" Retries are an availability mechanism, not a termination guarantee. A retry budget that is exhausted is itself another exit path that needs a terminal state. If an option offers "retry up to 3 times" as the complete answer, it is incomplete by construction.

Reference shape of the safeguard

async function runSession(sessionId, input) {
  await sessions.open(sessionId);                 // durable, status = IN_PROGRESS
  const deadline = Date.now() + SLA_MS;

  try {
    for (let turn = 0; turn < MAX_TURNS; turn++) {
      if (Date.now() > deadline) return escalate(sessionId, 'SLA_TIMEOUT');

      const res = await claude.messages.create({ ...ctx });

      switch (res.stop_reason) {
        case 'tool_use':
          ctx.messages.push(res, await runTools(res));   // errors → is_error tool_result
          continue;
        case 'end_turn':
          // Verification gate: did a terminal action actually occur?
          return (await verifyResolution(sessionId))
            ? resolve(sessionId, res)
            : escalate(sessionId, 'NO_TERMINAL_ACTION');
        case 'max_tokens':
          return escalate(sessionId, 'TRUNCATED_OUTPUT');
        case 'refusal':
          return escalate(sessionId, 'MODEL_REFUSAL');
        default:
          return escalate(sessionId, 'UNEXPECTED_STOP_' + res.stop_reason);
      }
    }
    return escalate(sessionId, 'TURN_BUDGET_EXHAUSTED');   // loop fell through
  } catch (err) {
    return escalate(sessionId, 'ORCHESTRATOR_EXCEPTION', err);   // never rethrow bare
  } finally {
    await sessions.assertTerminal(sessionId);   // invariant check: RESOLVED | ESCALATED
  }
}

Four structural features make this the "right answer" shape, and the exam looks for them:

  1. The switch is exhaustive with a default. A new stop reason escalates rather than falling through silently.
  2. The for loop's fall-through is handled. Exhausting the turn budget is an explicit escalation, not an implicit return.
  3. There is a verification gate on success. end_turn means "Claude stopped talking", not "the refund was issued". Verify against the system of record.
  4. There is an out-of-band sweep. finally asserts the invariant in-process; a separate reaper catches crashes, where no finally ever runs.

The handoff payload

An escalation that hands a human 4,000 lines of raw transcript has technically terminated the session and practically destroyed the SLA. A correct escalation is a structured handoff:

{
  "session_id": "sess_8823",
  "customer_id": "cus_401",
  "reason_code": "TURN_BUDGET_EXHAUSTED",
  "intent": "duplicate charge dispute, order #A-7741",
  "verified_facts": [
    { "fact": "two settled charges of $89.99 on 2026-08-02", "source": "payments.list_charges" }
  ],
  "actions_taken": [
    { "tool": "lookup_order", "result": "ok" },
    { "tool": "issue_refund", "result": "blocked: amount exceeds tier limit" }
  ],
  "blocked_on": "refund authority above $50 requires a human approver",
  "customer_sentiment_note": "second contact about the same issue",
  "suggested_next_step": "approve $89.99 refund under policy 4.2"
}

Note what is not in it: the raw model reasoning chain and the full turn-by-turn transcript. Carry facts and provenance forward; drop the narrative.

Correct-answer signals
  • Exhaustive stop_reason handling with a default branch
  • Durable session state + an out-of-band sweeper for crashes
  • Verification of the terminal action before declaring resolution
  • Structured handoff payload on escalation
  • Turn budget and wall-clock budget, both with an escalation path
Distractor signals
  • "Instruct the agent in the system prompt to always escalate if it cannot resolve"
  • "Detect completion by checking whether the reply contains 'resolved'"
  • "Increase max iterations to 50 so it always finishes"
  • "Retry the request up to 3 times" as the whole answer
  • "Have the model self-report whether it resolved the issue"

Q&A drill

Why is end_turn insufficient evidence that a support session was resolved?

end_turn means the model finished generating — nothing more. It fires identically for "I've issued your refund, confirmation #R-88" and for "I'm sorry, I'm not able to help with that." Only a check against the system of record (was a refund row written? was the ticket status changed?) distinguishes them. Resolution is a property of the world, not of the transcript.

Your orchestrator handles end_turn, tool_use, and max_tokens. What breaks?

Everything else falls through silently: refusal, stop_sequence, pause_turn, model_context_window_exceeded, and any value Anthropic adds later. The fix is not to enumerate more cases — it is to add a default branch that escalates on any unrecognised stop reason. Design so unknown states fail into escalation, not into silence.

The pod is killed mid-session by a deployment. Which safeguard covers this?

Only durable session state plus an out-of-band reaper. In-process constructs — try/finally, signal handlers, graceful shutdown — are best-effort and do not survive SIGKILL. The reaper queries for sessions in a non-terminal status past their SLA and escalates them. This is why "wrap the loop in try/finally" is a partial answer that the exam pairs against a full one.

Why is a bigger turn budget the wrong fix for sessions that end without resolution?

Because the budget is not the failure — the unhandled budget exhaustion is. Raising 10 to 50 moves the cliff and multiplies cost and latency by 5× for the sessions that were always going to fail. The correct change is to make exhaustion an explicit escalation with partial progress attached. Root cause over layering: a recurring exam theme.

What belongs in an escalation payload, and what must be left out?

In: session and customer identifiers, a machine-readable reason code, the interpreted intent, verified facts with their tool provenance, actions attempted and their outcomes, the specific blocker, and a suggested next step. Out: the raw reasoning chain, the full untrimmed transcript, and any model-generated confidence score. Humans need decision-ready facts with sources, not a replay.

An agent asks a clarifying question and stops. Resolved, or escalated?

Neither yet — it is AWAITING_CUSTOMER, a suspended state, and it needs its own timer. Suspended states are where silent drops hide: if the customer never replies, the session must age out into RESOLVED (via an auto-close policy) or ESCALATED. The invariant is that no session sits in a non-terminal state indefinitely.

Topic 2 · Permissions and hooks vs CLAUDE.md

Objective: Distinguish instructions that must be enforced through settings permissions or hooks from those appropriately placed in CLAUDE.md, and restructure configurations accordingly. Claude Code Config · 20%

The decision rule

Ask two questions about each requirement, in order:

  1. What is the cost of a single violation? If it is a security breach, a compliance finding, data loss, or money moving — it needs enforcement, because CLAUDE.md offers no guarantee.
  2. Can a machine verify it deterministically?
    • Verifiable before the action, from the tool call itself → permission rule (cheapest; no process spawned).
    • Verifiable only by running something (linter, test suite, scanner) or requiring a side effect (format, audit log) → hook.
    • Not mechanically verifiable — taste, convention, architecture facts → CLAUDE.md.
Rule of thumb the exam rewards Permissions answer "may this happen?". Hooks answer "what must happen around it?". CLAUDE.md answers "what should Claude know?". If a requirement contains the words never, always, must, or every, and a violation is expensive, it is not a CLAUDE.md requirement.

Permission rule syntax

{
  "permissions": {
    "deny": [
      "Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)",
      "Bash(curl:*)", "Bash(terraform apply:*)"
    ],
    "ask":  [ "Edit(package.json)", "Bash(git push:*)" ],
    "allow":[ "Bash(npm run lint)", "Bash(npm run test:*)", "Edit(src/**)" ]
  }
}
  • * matches within a path segment; ** crosses directory boundaries; ? matches one character.
  • Evaluation order is deny → ask → allow. A path in both deny and allow is denied.
  • additionalDirectories extends reachable directories; defaultMode sets the baseline interaction mode.
Trap — "we wrote it in CLAUDE.md and it mostly works" The exam's favourite restructuring scenario: a team documents a security rule in CLAUDE.md, observes ~95% compliance, and asks how to reach 100%. Adding emphasis, capital letters, or repeating the rule are all distractors. CLAUDE.md is delivered as context — there is no compliance guarantee at any font size. Move the rule to permissions.deny; if it must survive a developer editing project settings, move it to managed settings.

Restructuring a bloated CLAUDE.md

Given a 900-line CLAUDE.md that "Claude keeps ignoring", the graded fix is a four-way split:

  1. Security and irreversible-action rules → permissions.deny/ask (managed settings if org-wide).
  2. Mechanically checkable quality rules → hooks.
  3. Path-specific conventions → .claude/rules/*.md with paths: frontmatter, so they load only when Claude touches matching files.
  4. Multi-step procedures → skills, loaded on demand.

What remains in CLAUDE.md should be short, specific, non-contradictory project facts — under 200 lines. Note that @path imports improve organisation but not context cost: imported files load at launch too. Only path-scoped rules and skills actually defer the tokens.

Q&A drill

Compliance requires that Claude never read customer PII files. Where does that go, and why not CLAUDE.md?

permissions.deny, deployed via managed settings so no developer can override it. CLAUDE.md is advisory context: it shapes behaviour without guaranteeing it, which fails an audit by definition. Managed settings sit above project and local settings in precedence and cannot be excluded by users.

Why can't a permission rule enforce "all edited files must pass ESLint"?

Permission rules are evaluated against the tool call before it runs — tool name, command string, file path. Whether the resulting file passes ESLint is unknowable until the edit exists and the linter runs. That requires executing a process after the tool completes, which is precisely a PostToolUse hook.

A rule is in CLAUDE.md and followed ~95% of the time. Management wants 100%. What do you change?

The enforcement layer, not the wording. Restating the instruction more forcefully, putting it in caps, or repeating it in three files does not move a probabilistic mechanism to a deterministic one. Move it to a permission rule (if pre-checkable) or a hook (if it needs execution). This exact scenario is the archetype of the exam's "structural over probabilistic" principle.

When is ask the right answer instead of deny or allow?

When the action is legitimate but consequential enough to want a human in the loop: editing dependency manifests, pushing branches, touching migrations. deny would block real work and push developers to disable the config; allow gives away oversight. Candidates who forget ask exists over-choose deny — the exam sets that trap deliberately.

Team-wide TypeScript conventions are pushing CLAUDE.md past 400 lines. Best restructure?

Move them to .claude/rules/typescript.md with paths: ["src/**/*.{ts,tsx}"]. Path-scoped rules load only when Claude reads matching files, cutting baseline context while keeping the guidance available where it matters. Splitting into @path imports would organise the file but load exactly the same tokens at launch.

What is the precedence order of settings, and which layer can a developer not override?

Managed/enterprise policy → command-line args → .claude/settings.local.json → .claude/settings.json → ~/.claude/settings.json. Managed policy wins and cannot be overridden locally, which is why every "guarantee this org-wide" question resolves there.

Topic 3 · PostToolUse hooks as automatic quality gates

Objective: Implement PostToolUse hooks that automatically enforce code quality constraints — formatting, linting, test execution — after every file edit, independent of model instruction-following. Claude Code Config · 20%

Why PostToolUse specifically

The phrase "independent of model instruction-following" is the whole objective. A hook is a shell command, HTTP call, MCP tool, or sub-prompt that Claude Code executes at a fixed lifecycle event. It runs whether or not the model remembered, whether or not CLAUDE.md was read, whether or not the developer is watching.

EventFiresUse for
PreToolUseBefore a tool executes; can blockPrevention: block a dangerous command, deny a write to a protected path
PostToolUseAfter a tool completes successfullyVerification & repair: format, lint, type-check, test, scan, audit-log
UserPromptSubmitWhen the user submits a promptInject context; block off-policy prompts
Stop / SubagentStopWhen the main agent / a subagent finishes a turnEnd-of-turn gates: "the full suite must pass before you stop"
SessionStart / SessionEndOnce per sessionEnvironment prep; cleanup and reporting
PreCompactBefore context compactionPersist facts that must survive compaction
Prevent vs verify If the requirement is "this must never happen", you need PreToolUse — PostToolUse runs after the damage is done. If the requirement is "after every edit, X must be true", you need PostToolUse. Exam items hinge on this one word: prevent vs after.

Configuration anatomy

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/quality-gate.sh",
            "args": [],
            "timeout": 120,
            "statusMessage": "Formatting, linting and testing…"
          }
        ]
      }
    ]
  }
}
  • matcher — filters on tool name. Plain names and |/, lists are exact matches (Edit|Write); anything containing other characters is treated as an unanchored JavaScript regex (^Notebook, mcp__github__.*). Omitted or "*" matches every tool.
  • timeout — seconds. Give a test suite a realistic budget; a hook that times out is a hook that silently stops enforcing.
  • ${CLAUDE_PROJECT_DIR} — always anchor script paths to it. Relative paths break because the hook's working directory is not guaranteed.
  • Placement — .claude/settings.json (committed) for team-wide enforcement; settings.local.json for personal; managed settings for org-wide non-overridable gates.

The hook script contract

Input arrives as JSON on stdin. Output is communicated by exit code or by a JSON object on stdout.

Exit codeMeaningEffect on the session
0SuccessNothing blocked. stdout is parsed for a JSON decision if present
2Blocking errorstderr is fed back to Claude so it can fix the problem; on blocking-capable events the action is blocked
anything elseNon-blocking errorSurfaces as an error; execution continues
Exit 2 is the mechanism that makes the loop self-correcting On exit 2 the hook's stderr becomes Claude's next input. That is why your script must print the actual compiler/linter/test output — file, line, rule, message. A hook that fails with echo "lint failed" >&2 forces Claude to guess; a hook that pipes real diagnostics gets a targeted fix on the next turn.

A complete quality gate

#!/usr/bin/env bash
# .claude/hooks/quality-gate.sh — PostToolUse on Edit|Write
set -uo pipefail

INPUT=$(cat)
FILE=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')
[ -z "$FILE" ] && exit 0            # not a file edit; nothing to do
[ -f "$FILE" ]  || exit 0            # deleted/moved; nothing to do

case "$FILE" in
  *.py)
    black -q "$FILE"                             # 1. auto-repair silently
    if ! OUT=$(ruff check "$FILE" 2>&1); then    # 2. verify
      echo "$OUT" >&2                            # 3. real diagnostics to stderr
      exit 2                                     # 4. block; Claude sees stderr and fixes
    fi
    ;;
  *.ts|*.tsx)
    npx prettier --write "$FILE" >/dev/null 2>&1
    if ! OUT=$(npx tsc --noEmit -p tsconfig.json 2>&1); then
      echo "$OUT" | head -50 >&2
      exit 2
    fi
    ;;
esac

# Scope the test run to the touched area; a full suite per keystroke is unusable.
if [[ "$FILE" == src/payments/* ]]; then
  if ! OUT=$(npm test -- --findRelatedTests "$FILE" 2>&1); then
    echo "$OUT" | tail -60 >&2
    exit 2
  fi
fi
exit 0

Design points the exam rewards:

  • Auto-repair before you complain. Formatting is deterministic — fix it silently rather than blocking and burning a model turn on whitespace.
  • Scope the expensive checks. Related-tests-only, or path-gated. A hook that runs a 6-minute suite after every edit gets disabled by the team within a day, and a disabled hook enforces nothing.
  • Guard the trivial cases. Missing file_path, deleted files, unmatched extensions — exit 0 fast.
  • Bound the output. head/tail the diagnostics; dumping 10,000 lines of stack trace into context is its own failure.

JSON output for finer control

Instead of exit codes, a hook can print a JSON object:

{
  "decision": "block",
  "reason": "src/api/orders.ts:42  no-floating-promises  Promises must be awaited",
  "systemMessage": "Blocked by the repo lint gate",
  "continue": true
}

For PreToolUse the decision lives under hookSpecificOutput with permissionDecision (allow / deny / escalate) and permissionDecisionReason; updatedInput can even rewrite the tool call. Setting "continue": false stops Claude entirely — reserve it for genuinely unrecoverable states.

Trap — hooks are not a security boundary against a malicious operator Hooks are configuration, and configuration is editable. For guarantees an individual must not be able to disable, use managed settings (optionally with allowManagedHooksOnly), and back it up with server-side CI. A hook is a fast local gate, not the last line of defence.

Hooks vs CI — the layered answer

When an exam scenario says "quality has degraded since we adopted Claude Code", the strongest option usually combines both: a PostToolUse hook for fast local feedback that lets the model self-correct inside the session, plus branch-protected CI as the authority that cannot be bypassed. Options offering only CI ("just catch it in the pipeline") lose the self-correction loop; options offering only a hook are locally disableable.

Q&A drill

Why does a PostToolUse hook enforce a rule that CLAUDE.md cannot?

CLAUDE.md is text placed in the context window; adherence is probabilistic and degrades as the file grows and the session lengthens. A hook is executed by the Claude Code client at a fixed lifecycle event, with no model decision involved. That is the literal meaning of "independent of model instruction-following."

What exactly does exit code 2 do, and why does stderr content matter so much?

Exit 2 signals a blocking error and feeds the hook's stderr back to Claude. Because that text is the model's entire view of the failure, it must contain real diagnostics — file, line, rule ID, message. Generic text like "checks failed" produces guess-driven edits and a second failure.

The team's PostToolUse hook runs the full 6-minute suite after every edit. What's the fix?

Scope it: run only tests related to the edited file (e.g. --findRelatedTests), or gate the expensive run behind a path match, and move the full suite to a Stop hook or CI. The exam's failure mode here is not correctness but adoption — an unusable hook gets removed, and enforcement drops to zero.

Prevent a secret from ever being written, vs detect one after a write. Which events?

Prevention requires PreToolUse (inspect tool_input, return a deny permission decision or exit 2 before the tool runs). PostToolUse can only detect and remediate after the secret is on disk — by which point, for many compliance regimes, the incident has already occurred.

What matcher fires on every Edit and Write but not Read?

"matcher": "Edit|Write". Because it contains only letters and |, it is evaluated as an exact alternation list, not a regex. Omitting the matcher or using "*" matches all tools — including Read and Bash — which would run your formatter on nonsense input. MCP tools need their namespaced form, e.g. mcp__github__.*.

Should the quality-gate hook live in settings.json or settings.local.json?

.claude/settings.json, committed, so every team member gets the gate automatically. settings.local.json is gitignored and personal — enforcing a team standard there guarantees it applies to exactly one machine. For a standard that must survive a developer editing the project file, escalate to managed settings.

Topic 4 · Escalation decision criteria

Objective: Apply escalation decision criteria to determine when an agent should immediately honor a human escalation request versus attempt autonomous resolution using available tools. Context Management & Reliability · 15%

The one non-negotiable rule

An explicit human request is honoured immediately and unconditionally "Let me talk to a person", "transfer me to an agent", "I want a manager" — these are honoured on the spot. Not after one more tool call. Not after a "let me try to help you first". Not conditional on the agent judging the request unnecessary. Any option that attempts autonomous resolution first is wrong, even when it is framed as efficient, cost-saving, or better for the customer.

The reasoning the exam expects: the customer has made a decision about how they want to be served, and overriding it converts a routine transfer into a complaint. Deflection also breaks accessibility and regulatory expectations in banking and healthcare contexts. Sensible product behaviour is to escalate immediately and attach everything gathered so far — the transfer is fast and warm.

Why self-reported confidence is a trap, in one paragraph A language model's stated confidence is another token prediction, not a calibrated probability. It is systematically overconfident exactly where you need it most — on out-of-distribution requests the model has never seen — and it drifts with every prompt edit and model upgrade, silently changing your escalation rate with no code change and no alert. Deterministic triggers are observable, testable, loggable, and auditable. Confidence scores are none of those.

Autonomous resolution is correct when all of these hold

  • The customer has not asked for a human.
  • The intent maps to a documented policy and a supported workflow.
  • The required actions are inside the agent's authority envelope.
  • The tools needed are available and returning valid data.
  • The action is reversible or low-value, or has an explicit auto-approval threshold.
  • The session is making measurable progress toward a terminal state.

Break any one, and escalate. Note how this makes escalation a policy engine question, not a model question: the checks are evaluated in the orchestration layer, from observable state.

Where the criteria are implemented

Escalation logic belongs in the orchestrator as deterministic code — not as prompt instructions, because prompt-based escalation fails precisely in the sessions that have already gone wrong. A common correct pattern pairs the two: the model gets an escalate_to_human(reason_code, summary) tool for cases it recognises, and the orchestrator independently enforces the hard triggers regardless of what the model does. Belt and braces, with the deterministic layer as the authority.

Authority envelopes

Scenario questions in banking and e-commerce almost always turn on an authority limit. The design pattern:

  • Encode limits in backend tool logic, not in the prompt. issue_refund checks the tier itself and returns a structured "requires approval" error — so the limit holds even if the prompt is overridden by a jailbreak or a bad edit.
  • The tool's refusal should be actionable: what limit was hit, who can approve, and what the agent should do next.
  • The agent then escalates with the action pre-assembled, so the human clicks approve rather than re-investigating from scratch.
Escalation quality, not just escalation rate An escalation that arrives with verified facts, tool provenance, actions attempted, the specific blocker, and a recommended next step preserves most of the agent's value. Answer options that measure only "percentage escalated" are measuring the wrong thing — the metric that matters is human handling time after escalation.

Q&A drill

A customer says "just get me a human" while the agent is one tool call from resolving it. What now?

Escalate immediately. The proximity to resolution is irrelevant — the customer has exercised an explicit choice. The correct implementation still attaches everything gathered, including the nearly-complete resolution, so the human can finish in seconds. Options that finish the tool call "since we're so close" are wrong.

Why is "escalate when confidence < 0.7" a wrong answer even though it sounds quantitative?

Because the number is model-generated, not calibrated. It is overconfident on exactly the unfamiliar inputs that most need a human, it cannot be audited, and it silently shifts with prompt or model changes. The quantitative appearance is what makes it an effective distractor. Replace it with observable state: authority exceeded, policy gap, tool failure, no progress after N turns.

How should an agent handle a request that is in scope but exceeds its refund authority?

Escalate — and pre-assemble the action. Verify the facts, determine the correct refund, draft it, then hand off with the reason code (AUTHORITY_EXCEEDED), the evidence, and the exact approval requested. The limit itself must be enforced in the tool's backend, not merely stated in the prompt.

An incident agent has run the same three diagnostics twice with identical results. Escalate?

Yes — this is the "no measurable progress" trigger. Repeating the same tool calls with the same results is a loop, not investigation. The escalation carries the diagnostics already run and their output, so the on-call engineer does not repeat them. The detection should be deterministic: compare tool-call signatures and observed state across turns, don't ask the model whether it feels stuck.

Is sentiment analysis ever legitimately useful here?

As routing and prioritisation metadata — flagging a session for review, choosing a queue, adjusting tone — yes. As the gate that decides escalation, no. It misfires on terse writers, non-native speakers, and structured complaints, and it can be gamed. Keep it as an input to the human's context, never as the trigger.

Escalation rate jumped from 12% to 34% after a prompt change. What does that tell you about the design?

That escalation is being decided by the model, not by the orchestrator. A prompt edit should not be able to move an escalation rate 3×; if it can, your triggers are probabilistic. Move the hard triggers into deterministic orchestration code and the rate becomes a function of observable business conditions, with prompt changes affecting only the quality of the conversation.

Topic 5 · Extraction schemas: optional, nullable, and enum design

Objective: Design extraction schemas with optional fields, nullable values, and appropriate enum definitions that allow the model to accurately represent missing or ambiguous information without fabricating values. Prompt Engineering & Structured Output · 20%

The mechanism behind every question in this topic

A schema is a constraint the model must satisfy. If satisfying it requires inventing data, the model invents data. Marking po_number as required: ["po_number"] when 30% of your invoices have no PO number does not produce 30% errors — it produces 30% fabrications, because the model has no legal way to say "absent". The schema, not the prompt, is the root cause. This is the single most-tested idea in the structured-output domain.

The same logic applies to enums. An enum with five values and no escape hatch forces every sixth-category document into one of the five. The model is not being careless; the grammar leaves it no alternative.

Three distinct "missing" states — model them separately

StateMeaningRepresentation
AbsentThe document does not contain this field at allField optional (omitted), or null
Present but unreadableThe field exists but is illegible, cut off, or corruptednull value + a status enum member such as "illegible"
Present but ambiguousMultiple plausible readings (two dates, two totals)null or a candidates array + "ambiguous", plus a review flag

Collapsing all three into "missing" destroys your ability to route: absent fields are a business-rules problem, unreadable fields are a scanning-quality problem, ambiguous fields are a human-review problem. The exam rewards schemas that preserve the distinction.

A schema built the right way

{
  "type": "object",
  "additionalProperties": false,
  "required": ["invoice_number", "vendor_name", "total_amount",
               "currency", "document_type", "extraction_status"],
  "properties": {
    "invoice_number": { "type": ["string", "null"],
      "description": "Vendor's invoice identifier exactly as printed. null if not present." },

    "vendor_name":    { "type": ["string", "null"] },

    "total_amount":   { "type": ["number", "null"],
      "description": "Grand total including tax, as a number with no currency symbol,
                      thousands separators removed, decimal point as '.'. null if absent." },

    "currency": { "type": ["string", "null"],
      "enum": ["USD","EUR","GBP","INR","JPY","OTHER", null],
      "description": "ISO-4217 code. 'OTHER' if a currency is shown but not in this list;
                      null if no currency appears anywhere on the document." },

    "document_type": { "type": "string",
      "enum": ["invoice","credit_note","purchase_order","receipt","statement","other","unclear"],
      "description": "'other' = a recognised type outside this list.
                      'unclear' = cannot be determined from the document." },

    "po_number": { "type": ["string", "null"] },        /* optional in practice: nullable */

    "line_items": {
      "type": "array",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["description", "quantity", "unit_price"],
        "properties": {
          "description": { "type": "string" },
          "quantity":    { "type": ["number", "null"] },
          "unit_price":  { "type": ["number", "null"] }
        }
      },
      "description": "Empty array if the document has no itemised lines. Never invent lines."
    },

    "extraction_status": {
      "type": "string",
      "enum": ["complete","partial","illegible","ambiguous","wrong_document_type"],
      "description": "'partial' = some required business fields were absent.
                      'ambiguous' = multiple plausible readings were present."
    },

    "fields_not_found": {
      "type": "array", "items": { "type": "string" },
      "description": "Names of requested fields absent from the document. Drives routing."
    },

    "needs_human_review": { "type": "boolean" }
  }
}

The five design rules

  1. Required means structurally present, not semantically known. Keep the key required so downstream code never has to test for absence, and make the type nullable so the model can honestly say "not there". "type": ["string", "null"] is the workhorse. This is why "make every field optional" is a weaker answer than "keep keys required, make values nullable" — the former makes every consumer write defensive key checks.
  2. Every closed enum needs escape hatches. Two of them, doing different jobs: "other" = a real value outside your list (a taxonomy gap); "unclear" / "unknown" = cannot be determined (an evidence gap). One combined bucket hides which problem you have.
  3. Put the extraction contract in description. The description is prompt text the model reads. Format rules ("ISO-4217", "no currency symbol", "ISO-8601 YYYY-MM-DD") and null semantics belong there, next to the field, not buried in a system prompt.
  4. Model the outcome, not just the payload. extraction_status, fields_not_found, and needs_human_review turn a bag of values into a routable result — and they feed the feedback loop in Topic 7.
  5. Use additionalProperties: false. Prevents drift into invented keys and is required by strict schema enforcement.

Enforcement mechanisms

MechanismGuaranteesDoes not guarantee
output_config.format with json_schema (structured outputs)The response is valid JSON conforming to your schemaThat the values are correct
strict: true on a toolTool inputs match the tool's schema exactlyThat the tool was the right one to call
tool_choiceThat a tool is called at all (Topic 9)Anything about value accuracy
Trap — "add JSON schema validation to fix hallucinated values" Schema enforcement eliminates syntactic errors: malformed JSON, missing keys, wrong types, invalid enum members. It has no opinion about whether total_amount: 4820.00 is the number on the page. Semantic errors need schema design (nullability, enum escape hatches), targeted few-shot examples, and verification — not stricter parsing.

Practical limits to remember: structured outputs support enum, const, required, additionalProperties: false, anyOf, $ref/ $defs, and standard string formats. They do not support recursive schemas, external $ref URLs, numeric bounds (minimum/maximum), or string length bounds. Anything you cannot express in the schema — "total must equal the sum of line items", "date must be in the past" — belongs in a post-parse validation layer in your code.

Q&A drill

Purchase orders lack a PO number 30% of the time and the model invents plausible ones. Root cause?

po_number is a required, non-nullable string. The schema makes "absent" inexpressible, so the model satisfies the constraint the only way it can — by generating a value. Fix the schema: "type": ["string", "null"] with a description stating null when no PO number appears. No amount of prompt scolding fixes a grammar that forbids the truth.

Optional (omit the key) vs required-but-nullable. Which, and why?

Prefer required key, nullable value. Downstream code then always finds the key and only has to test for null, and your metrics can count nulls per field directly. Omitted keys make "absent" and "the extractor forgot" indistinguishable and force defensive checks at every consumer. Reserve true optionality for fields that are structurally irrelevant to whole document classes.

Why do you need both "other" and "unclear" in an enum?

They diagnose different problems. "other" says this is a real category you didn't list — a taxonomy gap, fixed by extending the enum. "unclear" says I cannot tell from this document — an evidence gap, fixed by better input quality or human review. Merging them into one bucket means you cannot tell which fix to apply, and both queues get triaged wrong.

Will structured outputs stop the model from misreading a total?

No. Structured outputs guarantee the response is schema-valid — well-formed JSON, right types, legal enum members. They say nothing about whether the extracted number matches the page. Semantic accuracy comes from nullable design, format instructions, targeted few-shot examples, and post-parse verification such as reconciling line items against the total.

Bank statements sometimes show two totals (with and without pending). How do you model that?

Do not force a choice. Either (a) give distinct fields — posted_balance and available_balance, both nullable — so the ambiguity dissolves, or (b) keep one field, set it null, record extraction_status: "ambiguous", list the candidates, and set needs_human_review: true. Either way the model never silently picks one. Forcing a single value is how you get a 50% error rate that looks like a 100% success rate.

Where do "amount must be positive" and "total must equal sum of line items" live?

In a post-parse validation layer in your application code. Structured outputs do not support numeric bounds (minimum/maximum) or cross-field arithmetic. Schemas constrain shape; business invariants are code. A correct architecture layers them: schema for shape, code for invariants, human review for what neither can settle.

Topic 6 · Extraction accuracy across varied document formats

Objective: Apply extraction accuracy patterns — structured schemas with optional fields, format normalization instructions, and few-shot examples — to reduce hallucination and improve consistency across varied document formats. Prompt Engineering & Structured Output · 20%

Diagnose before you prescribe

The exam's extraction scenarios always describe a symptom. Map it to a cause before choosing a fix, because each cause has exactly one right intervention and three plausible wrong ones.

Re-asking for a value that is not on the document just buys another fabrication at double the cost. Know which failure you have before you reach for retries.

Format normalization instructions

Put them in the field's description, where they sit adjacent to the field they govern:

"invoice_date": {
  "type": ["string", "null"],
  "description": "Invoice issue date normalized to ISO-8601 YYYY-MM-DD.
    Source documents use several conventions: interpret DD/MM/YYYY for EU vendors
    and MM/DD/YYYY for US vendors, resolving by the vendor's country when shown.
    If the order is genuinely ambiguous (e.g. 03/04/2026 with no country signal),
    return null and set extraction_status to 'ambiguous'. Do not guess."
}

Three things make this a model answer: it names the target format, it explains how to resolve the known ambiguity, and it specifies what to do when resolution is impossible. Instructions that say only "use ISO format" leave the hardest case undefined — and the undefined case is what produces silent errors.

Few-shot examples: target them

Few-shot capacity is scarce and expensive. Spend it where the model is actually failing.

High-value examples
  • The ambiguous cases that currently fail
  • A document where the field is genuinely absent → shows null being the right answer
  • One example per distinct layout family in your corpus
  • Contrastive pairs: two near-identical inputs with different correct outputs, teaching the discriminating feature
  • The edge formats: multi-page, rotated scan, handwriting, multi-currency
Wasted examples
  • Five more clean invoices that already extract correctly
  • Examples that only demonstrate the happy path
  • Twenty examples where five well-chosen ones would do — bloat costs tokens and dilutes attention
  • Examples that contradict the schema descriptions

Note the API also offers input_examples on tool definitions — schema-validated example inputs that ride alongside the tool schema. For format-sensitive tool parameters, that is often cleaner than stuffing examples into the system prompt.

The layered extraction pipeline

When a scenario asks for "a design that achieves 95%+ accuracy across heterogeneous documents", the graded answer is layered — no single lever gets there:

  1. Classify first. Route by document type/vendor to the right schema and example set. One universal mega-prompt for twelve document types underperforms twelve targeted ones.
  2. Extract with structured outputs, nullable fields, escape-hatch enums, format instructions, and targeted examples.
  3. Validate programmatically. Arithmetic reconciliation, referential checks against vendor/customer master data, date sanity, cross-field consistency. This is deterministic code, not a model call.
  4. Retry narrowly — only on the specific failed fields, with the validation error included as feedback, and with a bounded retry count.
  5. Route the residue to humans using needs_human_review, and capture what they correct (Topic 7).
Trap — the multi-pass review that reviews nothing "Have a second Claude call check the first one's output" sounds rigorous and is often a distractor. A second pass with the same context and no independent evidence largely reproduces the first pass's errors. Multi-pass review earns its cost only when the second pass has something new: the source document plus the candidate extraction to verify field-by-field, or a deterministic validator's error list to act on.

Measurement: segment or you're blind

"94% accurate" across a mixed corpus is a number that hides everything. Segment by document type × vendor/layout × field. A pipeline at 99% on invoice numbers and 61% on tax IDs for one vendor family averages beautifully and fails a specific business process completely. Segmented metrics are also what let you decide, per field, whether to automate or route to review — a per-field automation threshold beats one global one.

Q&A drill

Accuracy is 97% for Vendor A and 71% for Vendor B. What is the fix?

Add few-shot examples drawn from Vendor B's layout — the corpus is under-represented in the prompt, not fundamentally harder. If the layouts are structurally disjoint, classify first and route to a vendor-specific prompt and example set. Raising the temperature, adding retries, or switching models are all distractor moves that ignore the observed segmentation.

Dates come out in five different formats. Where does the fix go?

Into the field's description as an explicit normalization contract: target format, how to resolve known ambiguities (DD/MM vs MM/DD by vendor country), and what to emit when it cannot be resolved (null + ambiguous). Add one example per source convention. Post-processing with regex is brittle across new formats and cannot resolve genuine ambiguity.

When is a validation-retry loop the right answer, and when is it a waste?

Right when the failure is recoverable — a format violation, a reconciliation mismatch, a field the model could read correctly on a second, more focused attempt with the error fed back. Wasteful when the data is simply absent: the loop cannot conjure it and will either fabricate or burn its budget. Always bound the retry count and retry only the failing fields.

Is 30 few-shot examples better than 6?

Usually not. Beyond a small, well-chosen set, additional examples cost tokens, dilute attention, and risk contradicting each other. Six examples covering ambiguous cases, genuine absence, each distinct layout family, and a contrastive pair outperform thirty near-duplicate clean invoices. Choose by error analysis, not by volume.

The pipeline reports 94% accuracy but finance says it's unusable. What did the metric miss?

Segmentation. Aggregate accuracy hides a field or a document class failing badly — typically the one field a downstream process depends on. Break the metric down by document type, vendor/layout, and field, and set automation thresholds per field rather than globally.

Would the Message Batches API be a good way to cut extraction cost?

For an overnight backfill of historical documents, yes — ~50% cheaper and nobody is waiting. For documents extracted while a user waits, or inside a workflow that blocks on the result, no: the batch window can run to 24 hours. The exam plants Batch API in latency-sensitive scenarios specifically because the cost saving is real and tempting.

Topic 7 · Feedback loops from structured error metadata

Objective: Design feedback loop mechanisms that capture structured metadata about model errors and use those patterns to improve prompts, schemas, or few-shot examples in future iterations. Reliability / Structured Output

The shape of the loop

Capture → Classify → Aggregate → Diagnose → Intervene → Re-evaluate. Most real systems have step 1 and skip to step 5, which is why they never improve: an unclassified pile of corrections tells you that errors exist, not which change would remove them.

Why structured metadata is the whole objective Free-text notes ("this one was wrong, the date was off") cannot be aggregated. You cannot answer "which field fails most for which vendor, and is it a schema gap or a format gap?" from prose. A typed error record is what converts individual corrections into a ranked, actionable backlog.

The error record

{
  "record_id": "err_20260814_0912",
  "timestamp": "2026-08-14T09:12:44Z",

  "input_ref":     { "doc_id": "inv_88213", "doc_type": "invoice",
                     "vendor_id": "v_ACME", "layout_hash": "a91f",
                     "page_count": 3, "source": "email_scan" },

  "model_meta":    { "model": "claude-opus-5", "prompt_version": "extract-v7",
                     "schema_version": "invoice-v3", "example_set": "fewshot-v2" },

  "field":         "invoice_date",
  "model_value":   "2026-04-03",

  "error_class":   "FORMAT_MISINTERPRETATION",

The error taxonomy — this is the exam-relevant part

Each class maps to one intervention. That mapping is what the questions test.

Trap — "log everything and periodically review the logs" Reviewing raw logs is not a feedback loop; it is a hope. Without an error class on each record you cannot rank causes, cannot measure whether last month's change worked, and cannot tell a schema problem from a prompt problem. The exam-correct answer always names the structured classification step.

Versioning and closing the loop

Every record carries prompt_version, schema_version, and example_set. Without them you cannot attribute a change in error rate to a change you made, and "did v7 help?" becomes unanswerable. With them, the loop closes properly:

  1. Aggregate errors by class × field × vendor over a fixed window.
  2. Rank by count × severity × correction_cost — fix what is expensive, not what is frequent.
  3. Apply one intervention at a time, per the taxonomy mapping.
  4. Add the failing cases to a regression eval set before shipping the change.
  5. Re-run the eval; ship only if the target class improves and no other class regresses.
  6. Bump the version, and watch the next window's segmented metrics.
The regression eval set is the part candidates forget Corrections harvested from production are the highest-value eval data you will ever have: they are real, they are already labelled by a human, and they are precisely the cases your system fails. A feedback-loop design that captures errors but never turns them into a held-out eval set will oscillate — each fix quietly breaking a case an earlier fix addressed.

Same loop, agent edition

For agentic systems the record shape changes but the discipline does not. Capture per session: termination_reason, escalation_reason_code, tool-call sequence and failures, turn count, whether a verified terminal action occurred, and — where a human took over — what the human did differently. That last field is the gold: the delta between the agent's plan and the human's action is a labelled training signal for prompt, tool, and policy changes alike.

Q&A drill

Why won't free-text reviewer notes work as feedback-loop input?

They cannot be aggregated or ranked. You cannot compute "45% of high-severity errors are FABRICATED_VALUE on nullable-eligible fields" from prose, so you cannot choose between a schema change and a prompt change, and you cannot prove the change worked. Structure is what makes the data actionable.

Errors cluster as FABRICATED_VALUE on one field. Prompt fix or schema fix?

Schema. Fabrication on a field that is genuinely absent means the schema left no way to express absence. Make the value nullable (or add an "unclear" enum member) and state the null semantics in the description. Prompt instructions telling the model "do not guess" fight the grammar and lose intermittently.

Why version the prompt, schema, and example set on every error record?

Attribution. Without versions, an error-rate change could come from your fix, a model upgrade, a new vendor in the mix, or seasonality — and you cannot distinguish them. With versions you can compare like for like and detect regressions introduced by a specific change.

You have 20 improvement candidates and one sprint. How do you rank?

By frequency × severity × correction cost, not by frequency alone. A rare error that sends a wrong payment is worth more than a common cosmetic one. Then prefer interventions that are structural (schema, validator) over probabilistic (prompt wording), because they hold under drift.

What is the risk of shipping three prompt/schema changes in one release?

You lose attribution and can ship a net regression invisibly: one change helps, another hurts, and the aggregate looks flat. Change one variable per iteration, gated by a regression eval set built from real production corrections.

For a support agent, which single feedback field carries the most signal?

What the human did differently after escalation. It is a real, expert-labelled counterfactual for exactly the cases the agent could not handle, and it tells you which of the three levers to pull — a missing tool, a missing policy, or a prompt/authority gap. Escalation counts alone tell you only that something went wrong.

Topic 8 · Tool descriptions and selection reliability

Objective: Improve tool selection reliability by expanding tool descriptions with use-case examples, input format specifications, and explicit disambiguation guidance for semantically similar tools. Tool Design & MCP · 18%

The mechanism

Tool definitions are compiled into a system prompt. The model chooses a tool by reading its name, description, and input_schema — nothing else. It cannot see your implementation, your API docs, your Confluence page, or your intentions. Tool selection errors are almost always description errors, and Anthropic's own guidance is blunt about it: the description is "by far the most important factor in tool performance." Aim for at least 3–4 sentences; more for complex tools.

What a complete description contains

  1. What it does — the action, concretely.
  2. When to use it — the triggering user intents.
  3. When not to use it — and which tool to use instead. This is the disambiguation clause.
  4. Parameter semantics and formats — per parameter, in its own description.
  5. What it returns — and what it does not return.
  6. Caveats — latency, cost, side effects, irreversibility, rate limits.

The disambiguation problem, worked

An IT service-desk agent has three plausible tools for "I can't log in":

{
  "name": "search_knowledge_base",
  "description":
    "Full-text search over published IT self-service articles (how-to guides, known-issue
     notices, policy pages). Use this FIRST for any 'how do I…' or 'why is X happening'
     question, before opening a ticket. Returns up to 10 article summaries with
     article_id and relevance score; does NOT return ticket data and does NOT change
     any system state. Do NOT use for questions about a specific employee's account
     status or a specific open ticket — use get_ticket_status or check_account_status.
     Example queries: 'VPN certificate expired', 'how to request admin rights'.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": { "type": "string",
        "description": "Natural-language search phrase, 3-12 words. Do not include
                        employee names or ticket IDs." }
    },
    "required": ["query"]
  },
  "input_examples": [ { "query": "VPN certificate expired renewal steps" } ]
}
{
  "name": "check_account_status",
  "description":
    "Returns the current directory state of ONE employee account: enabled/disabled,
     lockout status, password age in days, MFA enrolment, and group memberships.
     Use when the user reports being unable to sign in, is locked out, or asks whether
     their access is active. Read-only — it does NOT unlock, reset, or modify anything;
     use unlock_account or reset_password for that. Requires the corporate employee_id
     (format 'E' + 6 digits, e.g. E004821), NOT an email address and NOT a display name;
     resolve an email to an employee_id with lookup_employee first.",
  "input_schema": {
    "type": "object",
    "properties": {
      "employee_id": { "type": "string",
        "description": "Corporate employee ID, format E###### (E followed by exactly
                        six digits). Uppercase E. Example: E004821." }
    },
    "required": ["employee_id"]
  },
  "input_examples": [ { "employee_id": "E004821" } ]
}

Every clause is load-bearing: the negative scope ("does NOT unlock") prevents mis-selection, the format spec prevents malformed calls, and the pointer to lookup_employee teaches the prerequisite ordering that Topic 9 formalises.

Write the negative scope explicitly For any two tools a reader could confuse, each description must say what it is not for and name the alternative. Models mis-select between semantically adjacent tools far more often than they mis-select between distinct ones, and the fix is a sentence, not a fine-tune.

Structured tool errors

An error message is a prompt: it is the model's only information about how to recover. Design it.

{
  "isError": true,
  "errorCategory": "PRECONDITION_FAILED",
  "isRetryable": false,
  "message": "employee_id 'jsmith@acme.com' is not a valid employee ID.",
  "attemptedInput": { "employee_id": "jsmith@acme.com" },
  "remediation": "Call lookup_employee with the email address to obtain the E###### id,
                  then retry check_account_status with that value.",
  "partialResults": null
}

Categories worth distinguishing: VALIDATION_ERROR (fix the input), PRECONDITION_FAILED (call something else first), NOT_FOUND (do not retry), RATE_LIMITED (retry after a delay), UPSTREAM_UNAVAILABLE (retry or escalate), PERMISSION_DENIED (escalate, never retry). Each one implies a different next action; a single "error": "failed" implies none.

Q&A drill

An agent keeps calling search_orders when it should call get_order_details. First fix?

Rewrite both descriptions with explicit positive and negative scope, each naming the other as the alternative, plus example inputs. Selection is driven by name, description, and schema — and only those. Reaching first for a stronger model, a system-prompt instruction, or a routing layer skips the actual root cause.

Why does a bigger tool catalogue reduce reliability?

Every additional tool adds a candidate to disambiguate among, consumes context window with its definition, and raises the chance of overlapping semantics. Reliability improves by consolidating related operations behind an action parameter, namespacing by service, and scoping the visible set per agent role.

Where do input format requirements belong — system prompt or parameter description?

The parameter's description, right where the model reads it while constructing the call. System-prompt format rules are distant from the decision point and get diluted in long sessions. For complex or nested inputs, add input_examples; for a hard guarantee, add strict: true.

What makes {"error": "Operation failed"} harmful rather than merely unhelpful?

It gives the model no basis to choose a next action, so it guesses: retrying non-retryable failures, abandoning recoverable ones, or fabricating a result to satisfy the user. A structured error with a category, a retryable flag, the attempted input, and a remediation hint turns a dead end into a recovery path.

Should a payments agent and a research agent share one tool catalogue?

No. Scope tools per role: read-only research tools for the research agent, mutating payment tools for the payments agent. This reduces selection ambiguity, saves context, and limits the blast radius if the agent is confused or manipulated. In Claude Code the equivalent is the subagent tools: allowlist / disallowedTools.

A tool returns 400 rows of JSON and the agent then loses track of the task. Fix?

Shape the response: paginate with metadata (total, has_more, next_cursor), return only high-signal fields, and include stable identifiers the model can chain into the next call. Dumping full datasets into context is a tool-design bug, not a context-window limitation.

Topic 9 · tool_choice and multi-tool sequencing

Objective: Configure the tool_choice parameter to guarantee tool invocation when structured output is required, and sequence multi-tool workflows so prerequisite data is obtained before dependent tools are called. Tool Design & MCP · 18%

The four values

ValueBehaviourUse when
{"type":"auto"}Model decides whether to call any tool. Default when tools are provided.Conversational agents where some turns need no tool
{"type":"any"}Model must call one of the provided tools, but picks whichEvery turn must produce a tool call — e.g. a router that must classify into one of N handlers
{"type":"tool","name":"X"}Model must call tool XGuaranteed structured output via a single extraction tool; a mandatory first step
{"type":"none"}No tools may be called. Default when no tools are givenForcing a natural-language turn — e.g. the final summary after data gathering
The behavioural side effect you must remember With any or tool, the API prefills the assistant turn to force a tool call. The model therefore emits no natural-language text before the tool_use block — even if you explicitly ask it to explain itself first. If you need commentary alongside the call, use auto and request the tool in the user message instead.

Two more constraints that show up as distractors:

  • Manual extended thinking (thinking: {type:"enabled"}) is incompatible with any and tool — only auto and none are supported. (Adaptive thinking, including models where thinking is on by default, does support forced tool use.)
  • Prompt caching: changing tool_choice invalidates cached message blocks. Tool definitions and the system prompt stay cached, but message content is reprocessed — so flipping tool_choice per turn has a real cost.

Forcing structured output

Two mechanisms, and the exam expects you to pick correctly between them:

GoalMechanism
The whole response must be a JSON object matching a schemaoutput_config.format with json_schema (structured outputs)
A specific tool must be invoked, with schema-valid inputstool_choice: {"type":"tool","name":"…"} + strict: true on that tool
Some tool must run every turn, model picks whichtool_choice: {"type":"any"}, optionally with strict: true

tool_choice guarantees that a tool is called; strict: true guarantees the inputs conform; neither guarantees the values are right. Layer all three ideas — force the call, constrain the shape, validate the semantics in code.

Sequencing dependent tools

The failure this objective targets: an agent calls process_refund(order_id) before it has an order_id, and either errors out or invents one. Four levers, strongest last:

  1. State the prerequisite in the description. "Requires an order_id obtained from lookup_order; do not call this tool until you have one." Cheap, and often enough.
  2. Return chainable identifiers. lookup_order returns {"order_id": "A-7741", …} — a stable machine identifier the next call can use verbatim. Tools that return only prose force the model to re-derive values it should be handed.
  3. Enforce the precondition in the tool backend. The dependent tool validates its input and returns PRECONDITION_FAILED with a remediation pointing at the prerequisite tool. This holds even when the model ignores the description — which is why it beats levers 1 and 2 in any question about guarantees.
  4. Stage the workflow in the orchestrator. For a fixed pipeline, don't ask the model to sequence at all: run stage 1 with tool_choice: {"type":"tool","name":"lookup_order"}, feed the result in, then run stage 2 with the dependent tool forced. Deterministic ordering by construction.
Staged tool_choice — the pattern worth memorising A three-stage banking dispute flow:
① tool_choice: {"type":"tool","name":"verify_identity"} — identity is non-negotiable and must be first.
② tool_choice: {"type":"any"} — the model picks among investigation tools, but must use one.
③ tool_choice: {"type":"none"} — force a natural-language resolution summary with no further side effects.
Each stage's guarantee is enforced by the API, not by the model's cooperation.

Parallel vs sequential

Claude can emit several tool_use blocks in one turn when the calls are independent — fetch customer, fetch order, fetch shipping status simultaneously. That is a latency win and the right default for independent reads. Where calls are genuinely dependent, parallelism is a correctness bug; sequence them. disable_parallel_tool_use: true forces one call per turn when you need strict serialization.

Trap — tool_choice: "any" as a fix for wrong tool selection any guarantees that a tool is called; it does nothing about which. If the agent is picking the wrong tool, forcing it to pick faster does not help. That is a Topic 8 problem — descriptions, disambiguation, consolidation, scoping.

Q&A drill

A classification service must always return a category, but sometimes replies in prose. Fix?

Force the call: tool_choice: {"type":"tool","name":"classify"} with an enum of valid categories in the schema and strict: true. Alternatively use structured outputs with a JSON schema. Adding "you must always use the classify tool" to the prompt is the probabilistic version of a guarantee the API gives you for free.

You set tool_choice: "tool" and the model stopped explaining itself. Bug?

No — documented behaviour. Forced tool use prefills the assistant turn, so no natural-language text precedes the tool_use block, regardless of instructions. If you need commentary, use auto and ask for the tool in the user message, or add a separate summarisation turn with tool_choice: {"type":"none"}.

Difference between any and tool, in one line each?

any: a tool must be called, the model chooses which. tool: this specific tool must be called. Use any when every turn must act but the right action varies; use tool when the step is fixed — mandatory identity verification, a single extraction schema, a required first stage.

An agent calls process_refund with a hallucinated order ID. Strongest fix?

Backend precondition enforcement: process_refund validates the order ID exists and belongs to the customer, and returns PRECONDITION_FAILED with a remediation pointing to lookup_order. Description hints and chainable identifiers help, but only backend validation guarantees it — the exam's structural-over-probabilistic principle applied to sequencing.

Three independent lookups for one customer. Sequence or parallelise?

Parallelise — one turn, three tool_use blocks, three tool_result blocks returned together. Sequencing independent reads triples the round trips for no correctness benefit. Reserve strict serialization (and disable_parallel_tool_use) for genuine data dependencies or ordered side effects.

Why can't you use tool_choice: "any" with manual extended thinking?

Forced tool use prefills the assistant turn, which conflicts with manual extended thinking's requirement to emit a thinking block first; the API returns an error. Only auto and none are compatible with manual thinking. Adaptive thinking does support forced tool use — know the distinction, because scenarios pair "we enabled thinking" with "we force tool calls" specifically to catch it.

Exam-day playbook

Read every question through this filter

  1. What actually failed? Name the root cause before looking at the options. Half the distractors are treatments for a different disease.
  2. Is the proposed fix structural or probabilistic? Config, schema, code, and API parameters beat prompt instructions every time.
  3. Does it fix the cause or add a layer on top of it? The exam consistently rewards removing the defect over compensating for it.
  4. Would this hold at 3 a.m. with nobody watching? If the answer depends on the model choosing well, on a developer remembering, or on a self-reported score, it is not the answer.
  5. Does it survive scale, failure, and restart? Crash, timeout, dependency outage, deploy.

Select-2 questions

Where a question asks for two answers, they are usually complementary layers, not two phrasings of the same idea — a deterministic control plus the mechanism that makes it usable (a hook plus CI; a nullable schema plus a review flag; forced tool use plus backend validation). If your two picks are near duplicates, one of them is wrong.

Time management

120 minutes / 60 questions = 2 minutes each. Scenario preambles are long but shared across several questions — read the scenario once, carefully, then answer its questions as a block. Flag and move on after ~3 minutes on any single item; the last-pass review with fresh eyes converts more marks than grinding.
